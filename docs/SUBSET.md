# SUBSET.md — Feature support matrix for Stator

## Overview

This document specifies which language features Stator compiles in each mode, and how. The four verdict values are:

- **static** — compiled to unboxed machine values (i32, f64, struct fields, function pointers); the default fast path.
- **dynamic** — compiled via tagged NaN-boxed values with shape tables and inline caches; used for untyped code and type-narrowed unions in `js` mode.
- **error(CODE)** — compile error, by design, with a permanent diagnostic code. Features marked as errors will never be supported in that mode.
- **not-yet(CODE, phase)** — planned feature; the diagnostic code and phase name indicate when support arrives.

Each row becomes ≥1 decision test (§4 Task 1.4 in plan.md) per mode, executable via `stator explain --json`.

This matrix operationalizes plan.md §1 (product spec). Rows must not contradict the starting matrix in plan.md §4 Task 1.1. Rows marked **[proposed]** represent language features not listed there but that implementers will encounter early (e.g., `for`-`of`, template literals, destructuring, exceptions); each is documented in the "Codes allocated by this document" section with a defensible verdict consistent with the plan's philosophy.

### Test262 feature-tag coverage

| Feature | `ts` mode | `js` mode | Notes |
|---|---|---|---|
| A pinned Test262 `features:` tag listed as generic not-yet in `tests/test262/features.ts` | not-yet(STA1214) | not-yet(STA1214) | Test262 tags identify broad semantic surfaces, often much wider than a landed Stator slice (for example, a tag for all typed-array or class-field semantics). The conformance runner therefore skips the whole tagged test until this matrix promises that full surface. The list is deliberately closed and regenerated only after reviewing a pinned corpus bump; an unknown tag is a runner error, never an implicit skip. |

### Mode semantics

`ts` mode rejects untyped code entirely; `js` mode accepts both `.ts` and `.js` files, treating untyped code as `Unknown` and lowering to the dynamic path (shape tables, inline caches, tagged values). One pipeline, two policy layers: file acceptance, diagnostic table, and typing of unresolved constructs.

## Syntax & control flow

| Feature | `ts` mode | `js` mode | Notes |
|---|---|---|---|
| `let`, `const` bindings | static | static if typed, else dynamic | Binding semantics are static; initialization and narrowing drive the static/dynamic split. |
| Function declarations, function expressions, arrow functions | static | static if typed, else dynamic | Closure capture via environment structs; untyped parameters widen to `Unknown`. In `js` mode calls may provide too many or too few arguments: extras are ignored and missing parameters receive `undefined`; `ts` mode retains the checker arity error. Capturing a binding declared *inside a loop* clones the heap environment each iteration (`perIterationEnv`) so each closure sees that iteration's value. An initializer's closure may read its own binding (`const g = (n) => … g(n - 1)`, `const o = { f: () => o.f() }`, plan.md §9 Task 6.28) when the function is only handed on, through parentheses, `as`, `?:`, `&&`/`\|\|`/`??`, an array element or an object-literal member. One the initializer may call before it finishes (passed to a call, coerced by `+`, spread) is not-yet (`STA1214`): Node throws a TDZ `ReferenceError` there, and the compiled program has no run-time TDZ check. Fixtures `subset_self_reference_initializer*`; goldens `ts|js/self_reference_initializer`. |
| `if` statements | static | static | Condition is evaluated; predicate narrowing is type-driven. |
| `while`, `do`/`while` loops | static | static | Control flow only. |
| `for` loop (C-style) **[proposed]** | static | static | Loop variable and bounds are typed; control flow is unboxed. |
| `for`...`of` loop over an array, a string, a Map, a Set, a `Uint8Array`, or a user class with `[Symbol.iterator]()` | static if the yielded type is typed, else dynamic | same | Specialized loops (docs/VALUE.md §4.13), no iterator object. Array length is re-read each step so a body that shortens the array stops early; strings are immutable so the bound is `jsrt_string_length`. A string yields **code points**, not UTF-16 units (`"👍"` is one iteration). A Set yields the element. A Map yields a `[key, value]` pair, which the HIR has no tuple for, so that binding is Unknown and a file that uses it is dynamic even when K and V are typed. Labels work on it like any other loop. A user class whose `[Symbol.iterator]()` returns a Generator (or a boxed specialized iterator) calls that method and drives the result with the existing iterator walk. `for-of` over anything with no static walk -- an Unknown value, a union, or a checker-refused non-iterable js mode admitted -- lowers through a `get-iterator` node to the runtime GetIterator dispatch (docs/VALUE.md §4.13): collections box, generators and stored iterators drive as-is, a user-iterable method resolves and runs, and the rest throw Node's catchable `TypeError` (plan.md §8 step 2a(c)). The explicit `c[Symbol.iterator]` spelling dispatches statically on a known user-iterable class (the read is the method's value, the call its invocation); `Symbol.iterator` as any other stored value stays `not-yet(STA1212)`, and the same spelling on an unknown receiver stays `not-yet(STA1214, Phase 8)` -- that spelling names the method without calling it, which is a value the dispatch does not build. |
| `for`...`in` loop | static if the object is typed, else dynamic | same | **Implemented (Phase 5 step 12 family b).** Desugars to `Object.keys` plus a counting `for`; key order is the Object.keys walk. An index-signature annotation is still not-yet (family d). |
| `switch` statement **[proposed]** | static | static if cases are typed, else dynamic | Control flow; case evaluation is type-driven. A clause that falls through into a later non-empty clause is a **ts-mode error** (`STA0012`, `noFallthroughCasesInSwitch`) and legal in js mode: it is valid JavaScript, so refusing it there would break §1.2's contract that untyped code is dynamic and never rejected (plan-notes 175). |
| `break` and `continue` **[proposed]** | static | static | Unlabeled and labeled control-flow redirection. |
| Labeled statements and labeled `break`/`continue` | static | static | **Implemented (Phase 5 step 12 family b for non-loop labels).** Compile to plain `goto`. A label on a block is breakable, not continuable. Unlabeled jumps use `goto` too, so a `break` inside a `switch` inside a loop cannot be captured by C's own binding rules. |
| Method value (`const f = o.m`) | static | static if the method is typed, else dynamic | **Implemented (Phase 5 step 12e, 2026-09-12).** The method's own `JSRTClosure` with `has_receiver`: `jsrt_call` prepends `undefined` when the receiver is omitted so `g(1, 2)` keeps argument positions; virtual dispatch uses `jsrt_method`. Unbound `this` that touches a property raises Node's TypeError (`jsrt_object_get_field`). Not `Function.prototype.bind`. Evidence: plan-notes 230. `super.m` is the same node with the receiver parameter as target and dispatch forced `direct` (plan.md §8 step 42; see the overriding row). |
| `fn.length` on a function value | static | static if the function is typed, else dynamic | **Implemented (plan.md §8 step 21b).** The declared arity, which never counts a method's receiver (docs/VALUE.md §4.16): a typed receiver reads the closure directly (`function-length` HIR node, `jsrt_closure_arity`), an untyped one answers through the dynamic property path (`jsrt_get_prop`). |
| The callee of a call is an ordinary expression | static | static if the callee is typed, else dynamic | **Implemented (Phase 5 step 12 family e).** `(up ? inc : dec)(x)`, `fns[0](x)`, `pick(false)(x)`, an IIFE, a function read out of a shape and then called. Nothing below the gate changed: `CallExpr.callee` was always an `Expression`, the emitter always evaluated it into its own rooted slot ahead of the arguments, and the verifier already required its type to be `fn` or Unknown (`STA4041`). Evaluation order is callee-then-arguments. The argument count is deliberately unchecked — JavaScript drops extras and fills missing ones with `undefined`, and the calling convention does that at runtime. A call through a class field (`o.run(1)` where `run` is a field holding a function) is also this row — field-access then `call`. Method values (`const g = o.m`) are a separate row below. A callee of statically-known non-function type throws Node's catchable `TypeError` after evaluating the callee and the arguments left to right (js-mode suppression of TS2349, plan.md §8 step 37) — `x is not a function`, named by the source spelling; an Unknown callee that turns out non-function aborts `STA2006` as before. Call-side spread is the rest-parameters row below. |
| Assignment to a function declaration's binding (`function log() {}` … `log = {}`) | error(STA0012) | dynamic | **Implemented (plan-notes 297).** The binding is mutable (§10.2.11); a compiled namespace IIFE publishes its object through it (`})(log = Debug.log \|\| (Debug.log = {}))`, TypeScript's own `_tsc.js`). js mode drops TS2630 and widens the binding to `Unknown`, so its slot holds the function and then whatever replaces it. `ts` mode keeps TS2630. Tests: `subset_function_binding_assign_js|ts`, `tests/golden/js/checker_type_refusals.js`. |
| `new` on an ordinary function (`function P(x) { this.x = x; }` … `new P(1)`), and `x instanceof P` | error(STA1003) — a `.ts` function has no construct signature, so `new P()` is an implicit `any` (TS7009 beside it as `STA0012`); classes are how ts mode constructs | dynamic | **Implemented (plan.md §11c T11.4 family 4, plan-notes 310; docs/VALUE.md §4.20).** `jsrt_construct` builds a dynamic object whose `[[Prototype]]` is `P.prototype`, runs `P` with it as `this`, and answers `P`'s return when that is an object (§10.2.2), so a factory-style constructor returning `{ … }` works and TS2350 is a js-mode runtime code. The callee may be any function VALUE the program wrote — `new Ctor()` through a variable, an allocator's `getSymbolConstructor()` — or an Unknown; an arrow, a method or a non-function is Node's catchable `X is not a constructor`. `instanceof P` walks the left side's prototype chain against `P.prototype`; a right side with no object `prototype` (an arrow) is Node's `Function has non-object prototype 'undefined' in instanceof check`. An instance prints as `P { x: 1 }`. A spread argument to `new` stays not-yet (the construct path takes no built list; docs/VALUE.md §4.23). Fixtures `subset_function_construct_js` / `_ts`, `subset_function_instanceof_js`; golden `js/function_constructors`. |
| Properties of an ordinary function: `f.count = 0`, `P.prototype.m = function () { … }`, `assert.same = …` and `assert.same(a, b)` | not-yet(STA1214, Phase 8) — ts mode would need a typed property layout on a closure | dynamic | **Implemented (plan.md §11c T11.4 family 4, plan-notes 310; docs/VALUE.md §4.20).** A function's own properties live in a dynamic table on its closure, created on the first write; `prototype` is its own slot, created on first observation, whose hidden `constructor` is the function. Reads, writes, the compound forms and calls (the function as the receiver) all go through the shape table, and an instance finds `P.prototype`'s members on its chain, getters and setters included. `F.prototype = { … }` replaces the prototype for later `new F()` (TS2565 is a js-mode runtime code); `name` and `length` stay read-only: the write is a `TypeError` whose message quotes the function's name where Node quotes its source text (`Function.prototype.toString` is not modelled). A function with properties prints them: `[Function: assert] { same: [Function (anonymous)] }`. `f.call`/`f.apply`/`f.bind` are `Function.prototype` members, not own properties, and stay not-yet (step 9). Fixtures `subset_function_prototype_js`, `subset_function_props_ts`; golden `js/function_constructors`. |
| Function declaration inside a block, loop or branch | static | dynamic | **Implemented (Phase 5 step 12 family e).** A module is always strict, so the declaration is BLOCK-scoped (ES2015) and Annex B's var-scoped alias does not exist. Hoisted to the top of its own block: `{ f(); function f() {} }` resolves, mutual recursion across one block works, and a loop body's declaration closes over that iteration's bindings because the initialisation re-runs per iteration. A `switch`'s clause list is ONE scope, not one per clause, so its declarations hoist across every clause and ahead of the dispatch. **Shadowing landed 2026-09-11** (plan.md §8 step 14, plan-notes 216): a block-level declaration that reuses a visible name — function, `let`, `const` or parameter alike — gets a HIR name of its own at the lowering, so it has a slot of its own and the outer binding survives the block. `subset_block_function_shadow_{ts,js}` moved from `not-yet` to `static`; `tests/golden/js/block_shadow.js` is the byte-for-byte proof. |
| Template literals **[proposed]** | static | static if interpolations are typed, else dynamic | String concatenation of typed values compiles to direct C concatenation; untyped interpolations use `jsrt_string_coerce()`. |
| User toString / valueOf: an object becoming a string (`` `${o}` ``, `String(o)`, `''.concat(o)`, `[o].join()`) or a number (`'' + o`, `Number(o)`, `<`, `==`, `parseInt(o)`) | static | static, or dynamic where the object is | **Implemented (plan.md §9 Task 6.27, plan-notes 345).** ECMA-262 §7.1.1 ToPrimitive and §7.1.1.1 OrdinaryToPrimitive: hint `string` tries `toString` first, hint `default` (`+`, `==`) and `number` try `valueOf` first; a Date's `default` is `string`. A method that is not callable is skipped, one that throws propagates as a catchable exception, and when both answer objects the conversion is Node's `TypeError: Cannot convert object to primitive value`. A class method, an object-literal method, an inherited one and a constructor's prototype method all answer. When the receiver's class declares the method the hint tries first, with no parameter and a primitive return, lowering emits the call itself (virtual where a subclass overrides it); anything else -- an interface, a union, an untyped value -- asks the object at run time (`jsrt_to_primitive`), and every conversion of an operand that may be an object is followed by a pending check. `Symbol.toPrimitive` stays refused until Phase 5 (`STA1212`, or `STA1214` for the computed member name that spells it). Arithmetic other than `+` on an operand the checker types as an object stays refused (`STA0012`, TS2362/TS2365, or `STA1214`), so the numeric operators meet a user `valueOf` only through an untyped value. Goldens `ts/to_primitive`, `js/to_primitive`; decision tests `subset_to_primitive_*`. |
| Spread operator `...` in array literals | static | static if spread source is typed, else dynamic | **Implemented (Phase 5 step 12).** Typed array/tuple operands lower to nested `jsrt_array_concat` over literal runs; `[...a]` shallow-copies via `concat(a, [])`, with a source's holes read as `undefined` (a spread iterates; docs/VALUE.md §4.4). A literal hole (`[1, , 3]`) stays not-yet. **Any iterable landed** (plan.md §11c T11.4 step 5, docs/VALUE.md §4.23): an Unknown, string, Map, Set, iterator or tuple operand drains through the `...` row (`jsrt_spread_operand`) before the `concat`, and a non-iterable throws `TypeError` (its message names the value, not V8's source text). A NARROWED match array (`RegExpExecArray`/`RegExpMatchArray`) spreads element-wise in both modes: the checker calls it an interface but at run time it is a dense array, so a first-position spread folds into `[].concat(m)` like every other position (plan.md §8 step 44a); an un-narrowed one stays the checker's TS2488. |
| Rest parameters `...args` | static | static if all consumers are typed, else dynamic | **Implemented (Phase 5 step 12 family a).** Callers already pass extra arguments; the callee packs `argv[i..]` into an array (`jsrt_args_rest`). `Function.length` excludes the rest parameter. Destructuring rest (`...[a, b]`) stays not-yet. **Call-side spread landed** (plan.md §11c T11.4 step 5, docs/VALUE.md §4.23): `f(...xs)`, `o.m(a, ...xs)` and `arr.push(...xs)` build the argument list as one array and call through `jsrt_call_spread_at`; a method is read through the shape table with its object as `this`, so a method spread is `dynamic` even over typed operands; a list whose pieces share one element type keeps a function call `static`. TS2556 is a js-mode runtime code. Still `not-yet(STA1214)`: a spread into `new` or `super(...)`, inside an optional chain, into a builtin namespace or fixed-arity builtin op (string methods, collection ops, the array callback ops, `toSpliced`), and in js mode into a function with an annotated TypeScript parameter (the call edge's `STA2001` has no position to check). Fixtures `subset_spread_call_*`, `subset_spread_method_call_*`, `subset_spread_super_call_*`, `subset_spread_optional_call_*`, `subset_spread_collection_*`, `subset_spread_array_callback_*`, `subset_spread_annotated_callee_js`; goldens `ts/iterable_spreads`, `js/iterable_spreads`. |
| Default parameter values | static | static if typed, else dynamic | **Implemented (Phase 5 step 12 family a).** Evaluated when the argument is `undefined` (missing or explicit). `Function.length` stops at the first default. |
| Optional parameters `x?` | static | static if typed, else dynamic | **Implemented (Phase 5 step 12 family a).** A missing argument is `undefined`; no initializer runs. `Function.length` still counts the parameter. JavaScript has no signature-order restriction, so a JSDoc optional parameter may precede a required one in `js` mode; `ts` mode keeps TypeScript's error. |
| Declaration without initializer `let x;` | static | dynamic | **Implemented (Phase 5 step 12 family a).** The slot starts as `undefined`. A typed read before a write (`let x: number; console.log(x)`) is TS2454: ts mode keeps the refusal (`STA0012`); js mode suppresses it and widens the binding to Unknown, so the read answers `undefined` and receivers go through the shape table -- a method call on the still-unassigned binding throws Node's catchable `TypeError` -- rather than trust the annotation (plan.md §8 step 2a(c)). A binding assigned before every use is never widened and stays fully static. |
| Object destructuring | static | static if source object is typed, else dynamic | **Implemented (Phase 5 step 12 family a).** A shallow pattern of identifiers desugars to field reads. Nested patterns, rename rest (`...r`), and defaults in the pattern stay not-yet. |
| Array destructuring | static | static if source array is typed, else dynamic | **Implemented (Phase 5 step 12 family a).** A shallow pattern of identifiers desugars to index reads. Nested patterns, rest, and holes-with-defaults stay not-yet. For-of destructuring stays Phase 6. |
| `try`/`catch`/`finally`/`throw` | static | static; catch binding is `Unknown` in `.js` without JSDoc type | **Implemented (Task 3.10).** Exception unwinding via landing pads (docs/VALUE.md §4.9): `jsrt_pending()` checks after every call, a per-try completion code routes `return`/`break`/`continue` through `finally`. The catch binding is `Unknown` in BOTH modes — anything can be thrown — so reading it is a narrowing point. What differs is whether the CHECKER lets you read it without narrowing: ts mode keeps `useUnknownInCatchVariables` and reports `STA0012`, js mode does not, because `catch (e) { e.message }` is ordinary JavaScript and §1.2 forbids rejecting it (plan-notes 175). A shallow identifier pattern on the catch binding is implemented (Phase 5 step 12 family a). An uncaught exception prints `Uncaught <value>` on stderr and exits 1. |
| `async` function declarations and expressions, `await` | static | static if typed, else dynamic | **Implemented (Task 4.6).** The body lowers to a state machine: one C function re-entered at a numbered resume point, with the locals that outlive an await living in a heap environment rather than on the stack. `await` is a suspend/resume pair over `jsrt_await` — it subscribes a native continuation to `jsrt_promise_resolve(operand)`, so awaiting a non-promise is legal and still costs exactly one tick, which is what makes an interleaving match Node's rather than merely finishing with the same answer. The prefix up to the first await runs synchronously on the caller's stack (observable, and the difference between an async function and a callback). A throw that escapes the body rejects its own promise via the landing pad, so `try`/`catch` around an `await` works with no new protocol. `main` drains the queue once after the module body: there are no timers and no I/O, so there is no macrotask phase. Deferred: `for await`, async generators, and async arrow/method forms not covered by the declaration and expression shapes. |
| Generator functions and `yield` | static | static if typed, else dynamic | **Implemented (Phase 5 step 8).** A `function*` is Task 4.6's resume machine driven by the caller: `gen()` only allocates, the body runs on the first `next()`, and `yield e` parks `e` then pops the C frame. A later `next(v)` is the value of that `yield`. Locals live in the heap environment for the same reason an async function's do. `for-of` over the generator discards the completion value; `next()` after `return` answers `{ value, done: true }`. Uncaught throws stay pending for the call site of `next()`. `.return(v)`/`.throw(e)` re-enter the parked body with an injection rather than a value: `throw` rethrows at the yield's own landing pad (the body's `try`/`catch` sees it exactly as if the `yield` threw), and `return` parks `v` and routes through every enclosing `finally` the way a real `return` at that point would — a `finally` that yields delays the answer, exactly per ECMA-262 27.5.1.3. On an unstarted or completed generator neither enters the body: `return(v)` answers `{ value: v, done: true }`, `throw(e)` rethrows to the caller. Deferred: generator methods and async generators (**STA1201**, receiver-in-env), `yield*` (**STA1214**), and `return`/`throw` on a boxed SPECIALIZED iterator (`arr.keys()`), whose object does not carry them (Node answers a TypeError the runtime cannot raise yet). |

## Types & typing policy

| Feature | `ts` mode | `js` mode | Notes |
|---|---|---|---|
| Type annotations (`: number`, `: string[]`, etc.) | static | static (where present) | Types are strictly required in `ts` mode; optional in `js` mode (inferred from code or JSDoc). |
| Interfaces and type aliases | static | static (where present) | Compile-time constructs; no runtime representation. |
| Explicit `any`, `as any` | error(STA1001) | dynamic | `ts` mode forbids `any` entirely (use `unknown` instead); `js` mode lowers to tagged values with dynamic dispatch. |
| Implicit `any` | error(STA1003) | dynamic | `ts` mode rejects untyped parameters and variables under strict mode; `js` mode lowers to `Unknown` (tagged, dynamic). |
| Union types | dynamic (tagged; narrowing = runtime check) | dynamic | **Implemented (Task 3.5), by having no union at all.** The HType model has no union node, so `string \| number` IS `Unknown` — and narrowing one therefore lands on exactly the machinery an `unknown` already needed, with no separate feature. A union whose constituents all map to ONE HType is that type instead: `"a" \| "b"` is a `string`, which is what makes `typeof` usable (its own type is a union of eight string literals). Discriminated unions checking a discriminant TAG are still deferred — that needs a union the model can see the constituents of. |
| `unknown` type | dynamic (narrowing = runtime check) | dynamic | **Implemented (Task 3.5).** A narrowed read emits `jsrt_check_number/string/boolean`, which returns the value or raises `STA2001` with a `file:line:col`. The check is per USE, not per binding: nothing proves the value did not change between two reads. An UNnarrowed `unknown` gets no check — printing one asks nothing of it — and a narrowing to a type no tag settles in constant time (an object, an array, a signature) leaves the value `unknown` on the dynamic path rather than being refused. |
| `as` casts | dynamic (boundary-checked) | dynamic | **Implemented (Task 3.5).** A cast off an `unknown` to a checkable type emits `jsrt_check_*`. An identity cast and a widening to `unknown` assert nothing and lower to the operand alone. A cast to a type no tag settles is DROPPED rather than believed: the value stays `unknown` and every operation downstream stays on the dynamic path, which is sound and costs nothing that compiles today. The older `<T>x` spelling is not accepted — it is ambiguous with JSX and adds a second syntax for a construct that has one. |
| `JSON.parse()`, FFI returns | dynamic (boundary-checked, always) | dynamic | **`JSON.parse` implemented (Task 4.2, tenth slice)** — see its own row below; it lands `unknown`, and the checks its uses need are exactly the ones `as` and narrowing already emit. FFI returns are still Phase 6. |
| Generic function declarations | static (monomorphized per concrete type tuple) | static, identically — a `.js` file cannot spell a type parameter, so a js-mode generic is a `.ts` file and gets the same specializations | Specialization happens AT the lowering, so no type parameter ever enters the HIR. Instantiations are shared by HType identity, which collapses literal types for free: `box(1)` and `box(2)` are one function. Depth is capped at 16 (STA2003) — `f<T>` calling `f<T[]>` has no fixed point. |
| Generic function used as a value, generic arrows, constrained or defaulted type parameters, explicit type arguments | static, or dynamic where the tuple is | same | Constrained, defaulted and explicit arguments specialize like any other call (the constraint is enforced by the checker, the default fills what no call determines). A generic read as a value takes the canonical tuple — every parameter its default, else `Unknown` — sharing its specialization with an undetermined call: printing it names the source declaration and dynamic dispatch through it runs the `Unknown` body, so the read is `dynamic`. `typeof` a generic folds to `"function"` without building a value. A callback to any call — ordinary, method, or receiver op (`arr.map(box)` passes `box<number>`) — specializes at the parameter's type, and an inline generic arrow or function expression passed directly as an argument does the same under a position-derived key (`arrow@file#offset<tuple>`): the literal is its own use site, so one tuple suffices. Still `not-yet(STA1214)`: an unassigned arrow or function expression anywhere but a direct call argument (a `let`, a nesting, a branch, a spread, a constructor argument — no single parameter type to read), one at an argument whose body reads an enclosing scope or a same-file `let`/`const`/`var` (no binding a module-level specialization could read), a NAMED declaration or homed arrow whose body reads the same (specializations lower before their file's statements, so the same reads refuse there too — plan-notes 280), a generic that escapes further (returned, stored — no use site names a tuple), a generic call at a generic type (self-application `box(box)` infers an argument type no monomorphic copy can spell), and `instanceof` against a generic class (one descriptor per tuple, so the bare name identifies nothing to compare against). |
| Generic classes | static (one descriptor per concrete tuple) | static, identically — a `.js` file cannot spell a type parameter, so a js-mode generic is a `.ts` file and gets the same specializations | A generic class specializes per concrete tuple at each `new` site, inferred or explicit; fields, methods, accessors and statics substitute with it. A non-generic subclass names one complete tuple explicitly (`class Sub extends Box<number>`): the base's layout is grounded once, and the descriptor, the inherited-method owner, the vtable and the super-call all name that tuple's specialization. A generic class nested in a function or block specializes in place, scoped to that evaluation exactly like a nested ordinary class; its name must be unique across the program and no enclosing scope may bind a type parameter the tuple would close over. Deferred, all `not-yet(STA1214)`: a generic subclass of a generic base (per-tuple bases), a raw or partial bound, an argument nothing binds, a nested subclass of a generic base, and `instanceof` against a generic class (one descriptor per tuple, so the bare name identifies nothing to compare against). |

## Objects & classes

| Feature | `ts` mode | `js` mode | Notes |
|---|---|---|---|
| Classes with fixed shape (no getters/setters) | static (fixed slot offsets) | static if fully typed, else dynamic | **Implemented (rung 6a).** An instance is one allocation: a pointer to a file-scope `JSRTClass` descriptor followed by its slots, with declaration order as slot order. A field read is an offset load, not a lookup. The slot list comes from the CHECKER's property list, not from the member nodes, which is why a `.js` class — whose fields are declared by `this.x = …` in the constructor and have no member node at all — gets the same layout with `unknown` field types. Methods occupy no slot: one function is shared by every instance and the call resolves at compile time to that class's method, so `o.m()` is a direct call with the receiver as argument zero. Statics, `#private`, inheritance, overriding, accessors and object literals have all landed on top of this layout — see the rows below, each of which says what it reduced to rather than what it added. In `js` mode (the checker's TS2339 suppressed, plan.md §8 step 37) a name the class never declared lives in the instance's overflow table (docs/VALUE.md §4.24): `c.missing = 2` grows it, a read answers what was stored or `undefined`, `c.missing()` calls what was stored or throws Node's `TypeError`, and `delete c.missing` removes it. Only the element spelling with a static key, `c["missing"] = 2`, still waits (`not-yet(STA1214, Phase 8)`). Fixtures `subset_absent_class_member*`. |

## Node built-ins — the `--node` platform (plan.md §11c T11.5)

`--node` is a platform flag, orthogonal to the mode (docs/MODES.md §6). A Node built-in is
`node:<id>` for any public id of the pinned Node's `builtinModules`, or the bare `<id>` where
Node accepts one (`path`, `fs/promises`); a bare built-in is never a package (docs/BUNDLER.md
§1). Under `--node` both spellings resolve to `packages/node/src/<id>.ts`, strict TypeScript over
`std`, and compile like any other module. `docs/NODE.md` is the per-member coverage.

## Notes and clarifications

- **Decidability:** Every row is testable via `stator explain --json` on a minimal program exercising that feature. Pre-Phase-1-implementation tests carry `// @expected-fail: true` and are reported (never hidden) by the test runner (§4 Task 1.4).
- **Boundary checks:** All "dynamic" verdicts rely on `jsrt_check_*()` functions at type-narrowing points. A runtime type mismatch is a located error, never silent corruption.
- **Specialization:** Features marked "static if typed, else dynamic" route to the static fast path only when the TS compiler can infer a concrete type. Untyped code in `js` mode takes the dynamic path using tagged `jsrt_value`.
- **Phase clock:** "Not yet" features are gated by the phase system in plan.md; out-of-scope features are permanently off v1's roadmap. No feature moves earlier than its phase without a plan amendment (plan §15.3).
- **Decision boundary:** The same feature may differ between modes because `ts` mode rejects untyped code outright (error), while `js` mode lowers it to the dynamic path (tagged values, shape tables, inline caches). This is by design (plan §1).
